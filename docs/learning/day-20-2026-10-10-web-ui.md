# Day 20 · 10 Oct 2026 · The web UI: a browser that talks to the API, and pages that watch a run live (PRs #51, #52, E10)

## Why
Everything so far is reachable only with `curl`. The web UI (E10) lets a visitor click "replay a scenario" and watch the agent work live, and lets the operator approve a fix with a button. Before writing any page, the API had to accept being called from a browser running on another website (Vercel), which browsers forbid by default.

## What we did (API side)
- **CORS** (`CORSMiddleware` in `main.py`): origins allowed by one regex with full-match semantics, `AEGIS_CORS_ORIGIN_REGEX`. By default it matches `localhost`/`127.0.0.1` on any port; production will match the UI's Vercel domains. GET and POST only. Allowed request headers: `Content-Type`, `X-Admin-Token`, `Last-Event-ID`. `Retry-After` is exposed so the UI can say "try again in N s" after a 429. No credentials.
- **`GET /incidents/{id}/runs`**: an incident's runs, newest first. The page opens the latest.
- **SSE resume:** the event stream honours the `Last-Event-ID` header. A browser's `EventSource` reconnects by itself after a network blip and sends the id of the last event it received; the server now continues from there instead of replaying the run from the start.
- **ADR-021:** the browser calls the API directly, not through a Vercel proxy.
- Tests: `test_cors.py` (allowed origin, preflight, rejected look-alike origins such as `http://localhost.evil.example`, the production regex against `https://aegisops.vercel.app.evil.example`), and an API test for the runs list and the resume.

## The decision: direct calls, not a proxy
The textbook way to avoid CORS is a proxy: the UI's own server forwards `/api/*` to the real API, so the browser sees one origin. We do not, for three reasons:

1. **Admission control would break.** ADR-018 identifies a visitor by the right-most `X-Forwarded-For` entry, which Google's front end writes with the address the request came from. Through Vercel, that address is Vercel's server for *everyone*: all visitors would share one "one run at a time" slot.
2. **Streams must stream.** A run's event stream stays open for minutes. Serverless functions have time limits and proxies may buffer.
3. **Nothing to hide.** The public API needs no secret. The operator token is typed by the operator, never baked into the site.

## How CORS works, step by step
```
Browser on https://aegisops.vercel.app wants POST https://aegisops-api…run.app/api/v1/runs/7/approve
   │  (custom header X-Admin-Token → not a "simple" request → ask first)
   ├─ OPTIONS /api/v1/runs/7/approve                       ← preflight
   │    Origin: https://aegisops.vercel.app
   │    Access-Control-Request-Method: POST
   │    Access-Control-Request-Headers: content-type, x-admin-token
   │  ← 200  Access-Control-Allow-Origin: https://aegisops.vercel.app
   │         Access-Control-Allow-Headers: … X-Admin-Token …
   ├─ POST /api/v1/runs/7/approve  (the real request)
   │  ← 200  Access-Control-Allow-Origin: https://aegisops.vercel.app
   └─ JavaScript may now read the response
```
A simple GET (an `EventSource`, the incidents list) skips the preflight, but the response still needs `Access-Control-Allow-Origin` or the browser hides it from the page.

## Terms introduced

**Origin.** Scheme + host + port, for example `https://aegisops.vercel.app`. Two URLs share an origin only if all three match.

**Same-origin policy.** The browser rule that a page's JavaScript may not read responses from another origin unless that origin agrees. It protects you: a random website cannot read your bank's API with your cookies.

**CORS (Cross-Origin Resource Sharing).** How an API agrees: response headers such as `Access-Control-Allow-Origin` list who may read. Enforced by the browser, not the server, so `curl` ignores it entirely. CORS is not authentication.

**Preflight request.** An automatic `OPTIONS` request the browser sends before a "non-simple" request (custom headers like `X-Admin-Token`, JSON bodies, methods other than GET/POST/HEAD) to ask whether it is allowed.

**Full match vs prefix match.** A regex must match the *whole* origin. With a prefix match, `https://aegisops.vercel.app.evil.example` would pass a check meant for `https://aegisops.vercel.app`. Starlette uses `fullmatch`; a test pins it.

**Reverse proxy.** A server that receives requests and forwards them to another server. It hides the backend, and also hides the client's address from it, which is why we did not use one.

**EventSource.** The browser's built-in SSE client: `new EventSource(url)`. It parses `event:`/`data:`/`id:` lines and reconnects automatically.

**Last-Event-ID.** The header EventSource sends on reconnect, carrying the `id:` of the last event received, so the server can resume.

## Interview questions
1. *Why didn't you proxy the API through Vercel to avoid CORS?* Visitor identity: per-visitor limits use the client address that Google's front end records; through a proxy every visitor becomes Vercel's IP. Also streaming limits, and there is no secret to hide.
2. *Is CORS a security control?* For the browser user, yes: it stops other sites from reading responses with the user's credentials. It does not protect the API from scripts or `curl`; authentication does that.
3. *What is a preflight and when does it happen?* An `OPTIONS` request the browser sends before cross-origin requests with custom headers, non-simple content types or other methods.
4. *How does an SSE client resume after a disconnect?* `EventSource` reconnects with `Last-Event-ID`; the server replays from the next sequence number. Our events have a per-run `seq`, so resume is exact.

## Part 2: the pages (PR #52)

### What we built
`apps/web`, a Next.js app with two pages:
- **Incidents** (`/`): scenario cards with **Replay investigation** (calls `POST /scenarios/{key}/replay` and jumps to the run), then the incident list with status filters and "Load more" (cursor paging).
- **Incident** (`/incidents/{id}`): a run selector, **Start / Investigate again**, and the run itself:
  - **Timeline**: every graph step in order, pending → working → done (or waiting / warning / failed), one plain-English line each, the raw event one click away.
  - **Hypotheses**, with the ones the investigation supported marked.
  - **Root cause and evidence**: claimed confidence vs confidence after the evidence check, the citations that held up, and the dropped ones crossed out with the reason.
  - **Proposed fix**: action, parameters, risk, rationale, the policy's reason; **Approve / Reject** for a signed-in operator; for visitors, a note that nothing executes.
  - **Outcome**: what the action did, then the post-fix check about 90 s later.
  - **Run stats**: model, duration, tool calls, tokens, cost.

### How a live run reaches the page
```
EventSource(/runs/7/events?after=N)
  └─ each event ─▶ mergeEvents (unique by seq, ordered) ─▶ buildSteps / hypotheses / evidenceView
                     └─ if the event changes the run row (verify_evidence, remediate, approval…)
                          ─▶ GET /runs/7 (root cause, proposal, decision, outcome)
server closes the stream ─▶ EventSource "error" ─▶ we close it ─▶ GET /runs/7
  ├─ still running  → reconnect after 1.5 s with after = last seq   (a dropped connection)
  └─ anything else  → stop                                            (paused or finished)
operator approves ─▶ POST /runs/7/approve ─▶ reconnect (the run is running again)
```

### Two bugs found by looking at real data
1. **The post-fix check vanished.** The first version closed the stream on the `run:end` event. But the verification result is stored *after* `end` (it runs about 90 s later), so a replayed finished run lost its last step. The server already closes the stream when there is nothing more, so the client now waits for that instead.
2. **React's compiler-era lint rule** (`set-state-in-effect`) flagged six places where an effect set state synchronously, which causes an extra render each time. The fixes made the code simpler: state derived during render (the shown run is "the fetched run *if* it is the selected one"), and state set only from callbacks (EventSource listeners, promise results).

### Why Next.js 16 and not the planned 15
Our dependency review fails a PR that adds a runtime dependency with a high-severity advisory. Next.js 15 bundles a PostCSS version with four such advisories, fixed only in 16. The first 16.3 releases had *critical* ones (remote code execution in image optimisation), fixed in 16.3.8, a security release. Rule: take security releases promptly; otherwise prefer a version that has had a couple of weeks to settle (16.4.0 was four days old). ADR-022.

### Testing a UI without a backend
- **Vitest** for the logic: the reducer, the stream hook (a fake `EventSource` the test drives event by event), the API client's error handling, and two components.
- **Playwright** for the pages: a production build, the API mocked at the network layer (`page.route`), run as a desktop browser *and* a Pixel 7. One assertion runs on every page: `scrollWidth - clientWidth <= 0`, meaning the page never scrolls sideways on a phone.

A lesson from doing it by hand first: headless desktop Chrome would not lay out narrower than about 500 px, so a "390 px" screenshot looked broken when the page was fine. Device emulation (Playwright's Pixel 7) gives the real phone viewport.

### More terms

**Client-side rendering (CSR).** The server sends a static page shell; JavaScript in the browser fetches the data and fills it. The opposite, **server-side rendering (SSR)**, fetches on the server before sending HTML. We chose CSR so a cold, scaled-to-zero API never delays the first paint.

**Pure function / reducer.** Same input, same output, no side effects. `mergeEvents` and `buildSteps` turn events into what the page shows; because they are pure, they are tested without a browser.

**React effect.** Code that runs after render to sync with something outside React (a subscription, a timer, a fetch). Setting state synchronously inside one causes an extra render; derive the value during render instead, or set it from the outside system's callback.

**useSyncExternalStore.** React's hook for reading a value that lives outside React (here: the operator token in `sessionStorage`), so every component sees the same value and updates together.

**sessionStorage.** Browser storage scoped to one tab, cleared when it closes. Where the operator token lives: never on the server, never in other tabs.

**Design tokens.** Named colours (`--surface`, `--ok`, `--bad`…) defined once for light and dark mode; components use names, never raw hex.

**Smoke test.** A few broad end-to-end checks that the main paths work at all; not exhaustive, but they catch "the page is blank".

**Network-level mocking.** Intercepting the browser's HTTP requests in the test (`page.route`) and answering them, so the real UI code runs against a predictable fake API.

**Device emulation.** Running the browser with a phone's viewport size, pixel ratio and touch settings; the honest way to check a mobile layout.

**Security release.** A patch version published to fix vulnerabilities; worth taking at once, unlike feature releases that are better left to settle.

### Interview questions (part 2)
5. *How does your UI show a run live, and what happens on a dropped connection?* EventSource on the run's SSE endpoint; events merged by sequence number (so duplicates are harmless); on close, check the run's status and reconnect with the last sequence number only if it is still running.
6. *Where do you keep logic in a React app so you can test it?* In pure functions outside components (the reducer and view derivations); components only render them. Unit-test the functions; smoke-test the pages.
7. *How do you test a UI whose backend is slow, paid or nondeterministic?* Mock at the network layer in Playwright with recorded payloads from real runs; keep one manual check against the real API.
8. *Why not the newest framework version?* Take security releases immediately; otherwise prefer a release that has had time to settle. Here: 16.3.8 (security) over 16.4.0 (four days old).
