# Day 3 · 16 Sep 2026 · OTLP ingest endpoint (PR #4, E1.1)

## What we did
Built `POST /ingest/v1/{traces,logs,metrics}`: OTLP/JSON parsing with Pydantic, pure conversion to rows, bulk insert, gzip and size caps, RFC 7807 errors. 25 tests, 98 % coverage, ~20k spans/s in-process. Also learned a GitHub lesson (PR #3 → #4).

## How a request flows
Collector → HTTP POST (gzip JSON) → `read_body` (content-type check, size cap, gunzip, size cap again) → `parse` (Pydantic `model_validate_json`) → `convert.*_to_rows` (pure functions: OTLP model → list of dicts) → `store.insert_*` (one `executemany` INSERT in one transaction) → `{}` or `{"partialSuccess": {...}}`.

## Terms introduced

**OTLP (OpenTelemetry Protocol).** The wire format for telemetry. Payloads are protobuf messages (`ExportTraceServiceRequest` etc.) sent over gRPC or HTTP. Structure: `resourceSpans[] → resource + scopeSpans[] → scope + spans[]`. Same nesting for logs and metrics.

**Protobuf and the JSON mapping.** Protocol Buffers is a binary schema-based serialisation. Every protobuf message has a canonical JSON form. OTLP/JSON *deviates* from it: trace/span ids are hex (not base64), and 64-bit integers are strings. We accept both hex and base64 (`normalize_id`) and `int | str` for int64 fields.

**Resource vs scope vs signal attributes.** *Resource* = who produced it (`service.name`, host, SDK). *Scope* = which instrumentation library. *Signal attributes* = facts about this span/log/point (`http.response.status_code`). We store signal attributes flat in `attrs` and the rest under `attrs["otel.resource"]`, `attrs["otel.scope"]`.

**Semantic conventions.** OTel's standard attribute names (`http.request.method`, `rpc.system`, `exception.message`). Because they are standard, tools can query `attrs->>'http.response.status_code'` across languages.

**Span kind and status.** Kind: SERVER, CLIENT, INTERNAL, PRODUCER, CONSUMER (which side of a call). Status: UNSET, OK, ERROR. Both arrive as int or name; `enum_name` normalises.

**Span events and links.** Events are timestamped annotations on a span; exceptions are recorded as an `exception` event with `exception.message`. Links point to related spans in other traces. Stored under `attrs["otel.events"]`/`["otel.links"]`. The exception event is gold for root cause.

**Metric types.** *Gauge* (a value now), *Sum* (a counter, monotonic or not, with *aggregation temporality*: CUMULATIVE since start or DELTA since last export), *Histogram* (bucket counts + explicit bounds + sum/min/max), *ExponentialHistogram* (buckets on a log scale), *Summary* (pre-computed quantiles). We store one row per data point; histograms keep `count` in `value` and buckets in `attrs["otel.histogram"]` so p95 can be derived later.

**Log severity number.** OTel's 1–24 scale (TRACE 1–4, DEBUG 5–8, INFO 9–12, WARN 13–16, ERROR 17–20, FATAL 21–24). `SEVERITY_NUMBER_WARN2` = 14.

**AnyValue.** OTLP's tagged union for attribute values (string/bool/int/double/bytes/array/kvlist). `to_python()` unwraps it recursively; a structured log body becomes compact JSON text.

**Content negotiation / 415.** `Content-Type` tells the server the body format. We accept only `application/json`; binary protobuf gets `415 Unsupported Media Type` with a hint (ADR-013).

**Content-Encoding: gzip.** The body is compressed; the server must decompress. The collector compresses by default, so this was required, not optional. We check the size limit before *and after* decompression to defeat a "gzip bomb" (tiny on the wire, huge inflated).

**413 Content Too Large.** Body over `AEGIS_INGEST_MAX_BODY_BYTES` (16 MiB). Configurable via settings.

**RFC 7807 problem+json.** A standard JSON error shape: `type`, `title`, `status`, `detail`, `instance`. All API errors use it via exception handlers, so clients parse one format.

**Partial success.** OTLP lets a server accept a batch but report how many items it dropped (`rejectedSpans`, `errorMessage`). We drop spans without valid ids and report the count instead of failing the whole batch.

**Idempotence and retries.** OTLP clients retry 5xx with backoff and never retry 4xx. So: malformed input → 4xx (drop, don't retry); DB down → 5xx (collector queues and retries; nothing lost within its queue).

**executemany / insertmanyvalues.** Passing a list of dicts to one `INSERT` makes SQLAlchemy batch rows into multi-row statements. This is why ingest is ~20k spans/s instead of ~500.

**Pure function.** No I/O, output depends only on input. `convert.py` is pure, so it is unit-tested with dict fixtures and no database.

**Dependency injection (FastAPI `Depends`).** `session: Annotated[AsyncSession, Depends(get_session)]` gives each request a session that commits on success and rolls back on error. Tests can override it.

**Fixture (test).** Reusable test data/setup. `tests/fixtures/otlp.py` holds realistic OTLP/JSON payloads with deliberately low-entropy ids so `detect-secrets` stays quiet.

**Coverage.** Percentage of code lines executed by tests. 98 % here; the missing lines are defensive branches.

**Throughput benchmark.** 20 batches × 500 spans through the in-process ASGI app: 0.44 s → ~22k spans/s. The point was to prove NFR-04 (≥ 500/s) with margin, not to optimise.

**Stacked PR.** A PR whose base is another unmerged PR's branch. GitHub *closes* it (cannot reopen) when the base branch is deleted at merge. PR #3 died this way; #4 was the rebased replacement. Rule: branch from main, or wait for the base to merge.

**Rebase.** Replaying your commits on top of a new base commit (`git rebase --onto main <old-base> <branch>`), then `push --force-with-lease`.

## Interview questions
1. *Why hand-write the OTLP parser instead of using the protobuf library?* The standard protobuf JSON parser decodes bytes as base64, but OTLP/JSON sends hex ids; also zero heavy dependency, and we only need a subset.
2. *How do you avoid losing data when the API restarts?* Return 5xx on DB failure so the collector retries; 4xx only for input that will never succeed.
3. *What is a gzip bomb and how did you defend?* A tiny compressed body that inflates to GBs; check size before and after decompression.
4. *Why one row per metric data point with buckets in JSON?* Keeps the schema simple now; p95 needs the buckets, which we still have; promote to a wide table only if a query needs it.
5. *How did you get 20k spans/s in Python?* Bulk multi-row INSERT in one transaction, pure conversion with no per-row I/O, async driver.
