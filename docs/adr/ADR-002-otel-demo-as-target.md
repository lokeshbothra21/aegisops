# ADR-002: The OpenTelemetry Demo (pinned v3.x) is the target system

**Status:** Accepted, 13 Sep 2026

## Context
An incident-response agent needs a system that actually fails. Options ranged from synthetic log generators to a real polyglot microservice application. Evaluation credibility depends on the faults being real, not generated by the same code that detects them.

## Decision
Use the OpenTelemetry Demo, a 15-service web shop maintained by the OpenTelemetry project, pinned to a release tag (3.0.0, recorded in `infra/otel-demo/VERSION`). It ships real OTLP telemetry from real SDKs in Go, Java, .NET, Python, Ruby, Rust, JavaScript and more, and it has 15 built-in fault switches driven by flagd feature flags.

## Alternatives considered
- **Synthetic log/metric generator.** Cheap, but the evaluation becomes circular: the generator's patterns are what the agent learns to find.
- **A self-written toy microservice app.** Weeks of work that is not the project, and faults would be contrived.
- **Sock Shop / Online Boutique.** Older, less telemetry, fewer built-in faults.

## Consequences
- Real traces have ~77 spans per request path and real semantic-convention attributes; the agent must cope with genuine noise.
- Minimal mode needs ~2.5 GB RAM on the laptop; the demo is stopped when not in use.
- Pinning to a tag protects against upstream breakage (the floating `latest` images broke on day one).
- Four held-out faults (S9–S12) are custom overlays on top of the demo because the built-in flags would otherwise all be "seen" during development (see ADR-010).
